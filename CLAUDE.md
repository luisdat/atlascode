## Remotes

- `origin` → `https://github.com/luisdat/atlascode.git` (this user's fork — push/PR work happens here first)

## Windows dev environment gotchas

- **`npm ci` fails on `postinstall`**: the script `cp ./scripts/githooks/* ./.git/hooks` ([package.json](package.json)) uses a Unix `cp`, but npm on Windows always shells scripts through `cmd.exe` by default — even when npm itself is invoked from Git Bash or WSL (if the resolved `npm` binary is the Windows-installed one, which it usually is via PATH interop). Fixes:
  - Quick: `npm ci --ignore-scripts` then manually run `cp ./scripts/githooks/* ./.git/hooks` in a POSIX shell (Git Bash/WSL have real `cp`).
  - Durable: `npm config set script-shell "C:\Program Files\Git\bin\bash.exe"` so npm always shells out through bash.
- **`vsce package` (via `npm run extension:package`) can fail even though the webpack build succeeds**: it runs its own preflight `npm list --production --parseable --depth=99999 --loglevel=error`, which can report spurious `extraneous`/`invalid` packages (e.g. after an `--ignore-scripts` install left some optional native/wasm packages — `@napi-rs/*`, `@emnapi/*`, `@tybys/*` — in an inconsistent state). This is safe to bypass: `node_modules` is excluded from the actual `.vsix` entirely ([.vscodeignore](.vscodeignore) has `node_modules/`), so `npx vsce package --no-dependencies --baseContentUrl https://raw.githubusercontent.com/atlassian/atlascode/main/` sidesteps the check without affecting what ships.
- **Node/npm on the Claude Code Bash tool's own PATH**: earlier in this repo's history this wasn't available (only the user's own separate WSL terminal had it) — but as of 2026-08-26 this Windows machine has `nvm4w` installed and `node`/`npm` resolve fine directly from the assistant's Bash tool (`/c/nvm4w/nodejs/node`, `/c/nvm4w/nodejs/npm`). Check with `which node npm` first rather than assuming either way, but don't assume it's unavailable and offload work to the user unnecessarily.
- **Every commit's pre-commit hook runs a full-tree `npm run lint`** (`eslint ./src ./e2e`, not just staged files) — see the CRLF/`core.autocrlf` gotcha below, which is the most common way this unexpectedly fails on a clean-looking change.
- **CRLF/LF churn making `git status` show hundreds of unrelated "modified" files, or blocking the pre-commit lint hook with thousands of `Delete ␍` prettier errors**: this Windows machine's **system-level** Git for Windows config (`C:/Program Files/Git/etc/gitconfig`) sets `core.autocrlf=true`, which conflicts with this repo's own [.gitattributes](.gitattributes) (`* text=auto` — meaning the repo already normalizes to LF for storage and expects checkouts to match). The two together cause files to check out as CRLF locally while git's blobs are LF, and `git status`/the lint step can disagree about whether that counts as "modified" depending on internal caching.
  - **Diagnose**: `git config --list --show-origin | grep -i autocrlf` — if you see `core.autocrlf=true` from a `Program Files\Git\etc\gitconfig` (system) line, this is the cause, even if a local override tries to set it to `false`.
  - **Durable fix** (assistant cannot run `git config` itself — hard rule, direct the user to run it): `git config core.autocrlf false` at the repo level. This makes the *effective* config correct, but does **not** retroactively fix files already checked out with CRLF on disk.
  - **Fixing already-corrupted files — `git restore .` is NOT reliably sufficient on its own**: it can skip rewriting many files based on a stale index/stat cache from before the config change, silently leaving CRLF bytes untouched on disk even though `git status` reports clean. The recipe that actually works is to force a full re-checkout with no shortcuts:
    ```
    git rm --cached -r .
    git reset --hard HEAD
    ```
    (Safe to run any time working-tree state is already fully committed/pushed — `rm --cached` only clears the index, and `reset --hard HEAD` rebuilds both index and working tree from the last commit; nothing is lost that wasn't already just index/checkout bookkeeping. Do the usual pre-destructive-command check first — `git status` — if there's any chance of real uncommitted work.)
  - Verify the fix with a raw byte check, not the `file` utility (which gave a false CRLF positive on this system even after files were genuinely all-LF): `grep -c $'\r' <path>` should print `0`.
- **Global git config had `user.name` and `user.email` swapped** (discovered 2026-08-24: `user.name` held the email string, `user.email` held the display name). This silently breaks anything that matches commits by author email — e.g. the Atlassian CLA-bot on upstream PRs, which will show the contributor as never having signed no matter what, because the "email" field isn't a valid email at all. Check `git config --global user.name`/`user.email` first if CLA-bot (or similar) checks mysteriously fail to match a real signature. The assistant cannot run `git config` itself (hard rule) — direct the user to fix it themselves with `git config --global user.name "<real name>"` / `git config --global user.email "<real email>"`, and to amend + force-push any already-open PR commits that were made under the broken config (`git commit --amend --author="Name <email>" --no-edit && git push --force-with-lease`).

## Contributing upstream (`atlassian/atlascode`)

- CLA required — [CONTRIBUTING.md](CONTRIBUTING.md) links the [individual](https://opensource.atlassian.com/individual) and [corporate](https://opensource.atlassian.com/corporate) CLA forms. The CLA-bot posts a comment/status (`context: "CLA"`) on the PR; it re-evaluates on each new push (force-push included) but can take a few minutes, and pushing an empty commit is a reliable way to force a re-check if it seems stuck.
- A separate bot may ask to "link your GitHub account to your Atlassian account" to enable **Rovo Dev automated code review** on the PR. This is a personal OAuth step only the PR author can do (the assistant cannot do this on the user's behalf). Even after linking, Rovo Dev review requires an internal Atlassian product license/seat — external contributors typically don't have this, and seeing "Rovo Dev couldn't review this pull request: the pull request author does not have access to Rovo Dev" is expected and **not a blocker**. Only the `CLA` context is an actual required/blocking status check; Rovo Dev review is purely an optional assist for maintainers.
- GitHub does not support deleting a PR (only closing) — if a PR's thread gets confusing (e.g. stale bot comments), close it and open a fresh one from a new branch off the same commit rather than trying to "delete and recreate."

## Known fix history

- **PAT credential collision across multiple Server/Data Center sites** (fixed 2026-08-24/25): `saveDetailsForSite` in [src/atlclients/loginManager.ts](src/atlclients/loginManager.ts) computed the stored credential ID's `siteId` as `site.product.key` (e.g. `"jira"`) for PAT logins instead of the site host, unlike Basic Auth which already used the host. Two different Jira/Bitbucket Server/DC instances authenticated via PAT with the same username hashed to the identical `credentialId` (`CredentialManager.generateCredentialId` = `md5(siteId::username)` in [src/atlclients/authStore.ts](src/atlclients/authStore.ts)), so connecting a second such site silently overwrote the first site's stored token (in-memory and in VS Code SecretStorage), causing the first site to fail auth and appear disconnected. Fixed by always scoping `siteId` to `baseLinkUrl` (the host) in that method, since it's only ever used for Server/DC (non-cloud) sites — the OAuth/cloud shared-credential-per-account design is separate and untouched.
  - Regression test: `src/atlclients/loginManager.test.ts` ("generates distinct credential IDs for different Server/Data Center hosts sharing the same PAT username").
  - Merged to this fork's `main` via PR #1.
  - Submitted upstream as `atlassian/atlascode` PR [#1933](https://github.com/atlassian/atlascode/pull/1933) (status as of last check: open, CLA passed, awaiting maintainer review — check `gh pr view 1933 --repo atlassian/atlascode` for current status rather than trusting this note indefinitely). An earlier attempt, PR #1932, was closed due to the CLA-bot/git-config issue above.
  - Unrelated, pre-existing, *intentional* single-site limitation not to confuse with this bug: cloud Jira sites added via API token are deliberately restricted to one at a time (`isSiteAddedViaToken`/`removeTokenConnectedSites` in loginManager.ts) — that logic only applies when `site.isCloud === true` and is orthogonal to the Server/DC PAT fix above.

- **Bitbucket PR description/comment images and attachment links** (fixed 2026-08-26/28): Bitbucket PR descriptions/comments render server-provided HTML verbatim (`htmlSummary`/`htmlContent` in [src/bitbucket/bitbucket-cloud/pullRequests.ts](src/bitbucket/bitbucket-cloud/pullRequests.ts) and [src/bitbucket/bitbucket-server/pullRequests.ts](src/bitbucket/bitbucket-server/pullRequests.ts)), with `<img>`/`<a>` tags pointing at Bitbucket's own auth-gated attachment URLs. A plain `<img>`/click-through `<a>` in the webview carries no auth header, so images showed as broken placeholders and attachment links opened externally with a 401/404.
  - **Images**: reused the same `RenderedContent` + `fetchImage`-retry-on-error mechanism Jira's issue view already had (`src/webviews/components/RenderedContent.tsx`) by wiring a new `FetchImageRequest`/`FetchImageResponse` IPC pair through to Bitbucket's pre-existing (but previously unused) `RepositoriesApi.fetchImage`, and switching `InlineRenderedTextEditor.tsx`/`NestedComment.tsx` off raw `dangerouslySetInnerHTML`.
  - **Attachment links**: VS Code's own webview link handling intercepts `<a href>` clicks and opens them externally *before* any page-level click listener gets a chance to `preventDefault()` it, so simply adding a click handler doesn't work — the fix strips the `href` attribute entirely off matching links (`download` attribute, or `/downloads/`/`/attachments/` in the path) as soon as they render, stashing the real target on a data attribute, then routes clicks through a new `FetchAttachmentRequest` action (reusing `RepositoriesApi.fetchImage` again) to an authenticated download + save-dialog flow.
  - **Non-obvious trap hit twice while building this** (worth remembering for any future webview-rendered-anchor work): when stashing a link's target for later use outside the webview's own DOM, always use `anchor.getAttribute('href')` (the raw attribute text), **never** `anchor.href` (the resolved property). For a relative URL, `.href` resolves against the *webview's own internal document base* — confirmed via live webview DevTools to be some `vscode-resource.vscode-cdn.net` pseudo-origin in a VS Code Remote/container setup, not the real site — silently corrupting the target. `.pathname` is safe to use (base-independent for a root-relative href), which is why the path-matching *detection* heuristic was never the bug, only the href *capture*.
  - Verified against a real Bitbucket Server PR (via direct REST API calls with a user-supplied PAT, and later live webview DevTools inspection) rather than assumptions — real attachment markup is `<a rel="nofollow" href="/rest/api/1.0/.../attachments/{id}">{real filename}</a>`, a relative URL ending in a numeric ID with the real filename only in the link text.
  - Confirmed working end-to-end by the user (both images rendering and a real attachment downloading from within the PR panel).
  - Merged to this fork's `main` via PR #2. Not submitted upstream as of 2026-08-28.
